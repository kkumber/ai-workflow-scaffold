# Workflow procedures

Shared policy is canonical in [AGENTS.md](../AGENTS.md); concrete project bindings and setup state are in [PROJECT.md](../PROJECT.md), navigation in [ARCHITECTURE.md](../ARCHITECTURE.md). Read only the procedure needed for the current work. This guide is not a mandatory startup read.

## Adoption and managed updates

Use the root [README.md](../README.md) for exact npx initialization, update, resolve and legacy-role migration commands. Installation alone does not place guidance at the project root or adapt it. Preserve existing instructions and the receiving project's manifest/README. Package and CLI copy only eight Markdown guides/forms plus three .codex/agents/*.toml roles; source TASK-* history is excluded, not deleted. Review legacy roles and staged TOML before explicit resolution; old custom roles are never automatically deleted.

Preserve active .ai-workflow-scaffold/ tracking/recovery state and follow the root README's update/resolve procedures.

## First-use procedure

If this is the first use or setup stage, the orchestrator must adapt the existing Markdown guideline files to the receiving project before starting application work. Use their existing structure as the reference: change specific project wording, stack/version details, paths, architecture entries, commands, and conventions; do not regenerate the documents or replace their shared policies. Final cleanup may remove obsolete setup-only sections and artifacts after their purpose is fulfilled.

1. **Detect:** read the setup record in PROJECT.md. Missing state, `template`, or `in progress` means setup is incomplete. A user setup request or observed mismatch between a `ready` record and the current project also requires a setup check. Do not initialize this scaffold source as an application when the user is maintaining the reusable template itself.
2. **Locate:** establish the receiving project root from the user's workspace and existing project configuration. Use paths relative to that root. Do not configure the installed package or this template source as though it were the receiving application. If a multi-project workspace has no unambiguous target, resolve the target before edits. If guidelines exist only in an installed dependency, integrate them into project-owned files first using the user's setup authorization; merge an existing AGENTS.md instead of replacing it. Do not patch dependency copies.
3. **Inspect:** after the scoped orientation in AGENTS.md, inspect the top-level structure, relevant manifests/lockfiles, existing local instructions, test/build configuration, and meaningful entry points. A bounded structure inspection is allowed for initial mapping; do not read all application source. Record evidence paths. A manifest constraint is not a verified installed version; a configured command is not a passed test.
4. **Bind:** set setup status to `in progress`. Make minimal edits to the project-specific fields and wording in README.md (or the existing root README using the project's filename convention), PROJECT.md, ARCHITECTURE.md, AGENTS.md, .codex/agents/\*.toml instructions, tasks/README.md, and reusable task forms only where needed. Adapt the root README's title, purpose, installation, and setup instructions to inspected project facts; merge existing content and preserve user customizations. Preserve valid TOML and the role names, medium backend/frontend reasoning, high reviewer reasoning, and omitted model selection unless the user explicitly changes these preferences. Model selection remains with the user's Codex session/default settings; do not add a per-role model or modify .codex/config.toml as routine setup. PROJECT.md is the canonical project blueprint for purpose, goals/objectives, feature catalogue, stack/tools and phased implementation, as well as concrete ownership paths and commands. Keep it concise and indexed; create linked specifications using the [modular layout](#modular-project-documents). Populate details from requirements, user decisions and inspected facts; reuse canonical specifications and keep unresolved values explicit. Reference it elsewhere rather than duplicating those facts. Apply AGENTS.md's lean-output rule: short project-specific bullets and required references, with no duplicate specifications or task history; preserve all mandatory shared rules. Preserve reusable headings, checklist fields, IDs/placeholders for future tasks, readability rules, role boundaries, test-first checks, approval requirements, and reporting style. Remove source-only references from live receiving-project guidance when their targets were not copied; do not rewrite historical task records or manufacture completed tasks.
5. **Clarify setup choices:** after inspection, ask targeted questions for unspecified or conflicting project purpose/goals, scope, included/deferred/excluded features, languages/runtimes, frameworks, key libraries, development/testing/delivery tools and intended phases. Reuse established facts and user decisions; do not ask again for known answers. Missing exclusions do not mean “none.” Recommendations must remain proposals until the user chooses. Wait for answers before finalizing AGENTS.md and PROJECT.md or marking setup ready; drafts may remain `in progress`. Record decisions and reasons in PROJECT.md; keep AGENTS.md aligned through references rather than duplicated inventories. Check every setup detail across the setup record, adoption fields, overview/index, linked specification/feature/phase documents and related project bindings, not just the categories listed here. Each must have one recorded disposition: filled from inspected evidence or user answers (with source); not applicable (with an evidence-backed or user-confirmed reason); or deferred with explicit user agreement. For each deferral record the actual agreement, unresolved detail, impact, owner, dependent work that must wait and next resolution action. Do not infer agreement from silence, a missing answer, or an agent's judgment that a detail is nonblocking. Keep setup `in progress`, ask about remaining details, and do not finalize either document while any detail lacks an allowed disposition. Do not invent a stack, business rules, architecture, tooling or layout, install dependencies, or create an application to fill fields. For a blank project, map only observed files; mark absent roles not applicable only with an observed reason.
6. **Clean up:** after receiving-project bindings are established, remove obsolete scaffold wording, example commands, one-time installation/adoption tutorials, completed setup checklists, and source-only maintenance sections that no longer serve the project. Setup-only sections and their headings may be removed despite the initial structure-preservation rule. Keep real project installation instructions and reusable setup/resume rules. Remove a scaffold-only file or folder only after inspecting its contents and references and confirming it is disposable, contains no user work or required evidence, and is no longer used. Record exact removals and reasons in PROJECT.md before deletion. Verify resolved targets stay within the receiving project and delete only identified artifacts; never use a blanket tasks/ or TASK-* deletion. Preserve shared policies, useful project content, active roles, tasks/README.md task-operation guidance, tasks/_template/ future forms/placeholders, the receiving project's actual task history, and setup evidence/status. Do not delete or personalize installed dependency/cache copies. Retain uncertain items and record the question instead of guessing. This cleanup applies to adoption, not maintenance of this reusable scaffold source.
7. **Verify:** check edited paths/links against actual files, ownership consistency, requirement references, preserved policies, configured commands, and cleanup removals. Repair references to removed content and confirm the remaining workflow is usable. Record which checks ran and which commands were only discovered. Do not claim application verification from document inspection. Record affected files, evidence, limitations, and next actions in the setup record and task evidence when a task exists.
8. **Finish:** set status to `ready` only when the target is identified, relevant bindings are accurate, applicable cleanup is complete, links resolve, shared policies are preserved, every setup detail satisfies step 5's recorded completion rule, and no unanswered setup decision remains. Report adapted files, removed wording/sections/files/folders with reasons, retained uncertain items, and remaining unknowns. `ready` means documentation is configured, not application tests passed or deployment is ready. On later reads, retain a matching ready configuration; update only changed bindings or explicit user requests. Resume partial setup without wiping completed entries or user customizations.

This is a narrow, orchestrator-only documentation setup permission, not authorization to implement application features, add dependencies, execute migrations or deploy. It requires no separate application checkpoint; report direct document checks and honor higher-priority permissions. Later application work follows the [risk-based classification](../AGENTS.md#classify-the-change-and-select-verification); only test-first steps require the extra checkpoint. Reviewers report setup gaps without adaptation edits. Preserve conflicting existing policies and resolve them rather than silently weakening either policy.

Installing a package does not by itself ensure that the host reads its AGENTS.md or places guidelines in the project root. Markdown guidance alone does not implement package delivery; verify the actual CLI/copy path described in the [root README](../README.md) before claiming first-use setup is reachable.

For managed updates, follow [preservation and conflict handling](../README.md#update-an-adopted-project). Do not reset tracking state, reintroduce deliberately removed setup sections merely to match a template, or count a clean text merge as application verification.

## Create a task

For small direct low-risk work, use the [compact form](_template/plans.md#compact-direct-work): one entry in an existing relevant plan or a new plans.md, without mandatory todo/done files. Keep goal/authorization, risk/files/approach/check selection, actual evidence/review/limits and current status. For test-first or complex/multi-step work, select an unused TASK-NNN ID, use the short/expanded plan and derive [todo.md](_template/todo.md) and [done.md](_template/done.md). Remove unused form instructions; preserve applicable criteria, cases and approvals. Do not delete existing records or fabricate completion. Planning-only requests stop before implementation.

The plan is canonical for requirements, applicable cases/approval and actual results. A compact direct entry also owns pending/completed state. Where separate ledgers are used, todo holds pending actions/state and done references completed IDs/evidence. Update changed facts at meaningful transitions without reproducing inventories or logs. History is retrieved for relevant decisions, not routine startup reading. Keep commands/results and meaningful failure excerpts attributable; exclude secrets/private data.

## Plan, start or resume an implementation phase

1. **Consult:** before planning, starting, or resuming a phase, apply relevant goals/features and stack/tools/constraints from PROJECT.md, plus the selected phase document and relevant linked specifications. Reuse current context under the [scoped-reading policy](../AGENTS.md#scoped-context-before-work); use the [index](../PROJECT.md#reading-index) only for needed reads.
2. **Align:** link applicable PHASE/FEAT/GOAL IDs, consulted sections and prerequisite evidence in the task plan. Chat requirements are valid task inputs; absence from PROJECT.md alone is not a blocker or reason for a full reread. Record task-specific requirements in the plan; update PROJECT.md only for changed project/phase facts. Check scope, dependencies and entry/exit criteria against evidence; resolve consequential gaps/conflicts with the orchestrator before affected implementation. Existing inspection, ownership, risk classification and step-approval rules still apply.
3. **Maintain:** update brief project decisions and roadmap status in PROJECT.md, details in their canonical specification/phase files, task cases/approvals/results in the task plan, and affected navigation in ARCHITECTURE.md. Mark phases complete only with exit evidence; retain unfinished work and next dependencies. Roadmaps authorize no implementation or release actions by themselves.

## Modular project documents

- PROJECT.md owns brief project summaries, constraints/gotchas, concrete bindings and feature/phase indexes.
- During AI setup, create `plans/PROJECT-SPEC.md` for detailed project/stack/tool specifications and `plans/features/FEAT-NN-name.md` for features needing separate detail. Reuse existing canonical specs instead of duplicating them.
- Create `plans/phases/PHASE-NN-name.md` for each agreed phase. Keep stable IDs; include scope/GOAL/FEAT links, dependencies, sequencing, entry/exit criteria, risks, handoffs and task links.
- Read only the needed [specification form](../tasks/_template/plans.md#project-specification-template), [feature form](../tasks/_template/plans.md#feature-specification-template) or [phase form](../tasks/_template/plans.md#phase-specification-template). These on-demand forms ship in the existing task form; the initializer does not copy a prepopulated plans/ tree. Source plans/ README files only illustrate the generated layout.
- Preserve existing content and user decisions when extracting details; repair references and link actual files before finalizing setup. No placeholder path is a completed specification. Apply the first-use completion rule to all linked documents; create no invented phases/features.
- Phase/specification documents own requirements and sequencing; task records own step cases, approvals and execution evidence. Update changed facts only and reference canonical evidence instead of copying logs.
- On phase planning/start/resume, follow PROJECT.md to the selected phase and relevant dependencies. Reuse unchanged context; do not load every plan, specification or template for a new task.

## Marketing SEO checklist

Frontend must read this complete checklist before planning, changing or reviewing public marketing/content pages or affected metadata, crawlability, social previews or search-discovery behavior. Other owners read the relevant portions when their assigned changes affect those contracts. Derive relevant criteria and verification from it; internal/private applications do not become indexable by default.

Treat SEO as a core acceptance concern for public marketing websites, landing pages, and other content intended for search discovery. Plan it alongside content, accessibility, and performance. Establish the audience, page purpose, search intent, approved keyphrases, public domain, and indexing requirements from project evidence and the active plan. Apply only relevant checks to internal applications or deliberately private pages; do not make them indexable by default.

- **Search intent and keyphrases:** give each important page a clear topic and useful, original content that answers its audience's needs. Use approved primary and related keyphrases naturally in titles, headings, visible copy, descriptive links, and appropriate URLs. Avoid keyword stuffing, hidden text, invented search-volume claims, or treating a meta keywords tag as an optimization strategy.
- **Page metadata:** provide a unique, descriptive `<title>` and useful meta description for each indexable page. Use the framework's established metadata system, the correct document language and viewport, and an accurate absolute canonical URL where appropriate. Ensure route-specific metadata updates correctly; avoid duplicate tags and leaking development domains or placeholder branding.
- **Semantic HTML:** use meaningful landmarks such as `header`, `nav`, `main`, and `footer`, plus `article` and `section` where appropriate. Give each page a clear primary heading and a logical heading hierarchy. Use real anchor links with descriptive text for navigation, buttons for actions, accessible labels, and meaningful image alternatives; decorative images use empty alt text. Do not choose tags only for their visual styling or add keyphrases to unrelated alt text.
- **Open Graph and social media:** supply accurate `og:title`, `og:description`, `og:type`, `og:url`, and `og:image`, plus image alt text and dimensions when known. Add suitable social-card metadata for the intended platforms. Use approved, relevant preview media with absolute, publicly reachable URLs and valid media types. Keep preview titles, descriptions, canonical URLs, and branding consistent with the page; verify media availability and actual previews where tooling permits. Social previews support sharing and are not a promise of search ranking gains.
- **Crawlable content and routes:** make important copy, metadata, and navigation available to crawlers using the project's established rendering approach. Prefer server-rendered or statically generated marketing content when supported; do not assume every crawler or preview service executes client JavaScript. Use stable, meaningful URLs and crawlable links. Verify intended status codes, redirects, canonical behavior, and missing-page behavior through the responsible owner.
- **Indexing and discovery:** coordinate accurate sitemap entries, robots directives, canonical rules, and `hreflang` for actual localized equivalents when relevant. Include only intended canonical, indexable URLs in sitemaps. Check that public production pages are not accidentally marked `noindex`; keep staging/private content protected according to project requirements. Robots directives are not access control. Server headers, redirects, authentication, and infrastructure changes require their assigned owner and the checkpoint when classified test-first.
- **Structured data:** use relevant supported schema only when it accurately represents visible page content and verified business facts. Validate it with appropriate tooling when applicable. Never fabricate reviews, ratings, locations, offers, or eligibility claims to obtain rich results.
- **Media and performance:** optimize image formats, responsive sizes, compression, dimensions, fonts, scripts, and loading behavior. Avoid lazy-loading the primary above-the-fold image when it harms loading performance; defer offscreen media where appropriate. Check mobile usability, layout stability, and relevant Core Web Vitals using available evidence. Do not trade away accessibility or useful content for an audit score.
- **Verification and handoff:** select SEO checks from the affected pages, requirements and changed behavior. Inspect relevant initial HTML/rendered output, titles/descriptions/canonicals, headings, indexability, links and social media assets. Small copy/style edits do not automatically require a full browser/SEO audit, production build, performance measurement or every checklist item to be rerun. Use focused inspection/existing tests/browser checks where appropriate; broaden for affected behavior, uncertainty, failures or explicit requirements. Record actual results, inaccessible production-only checks and remaining owner actions; distinguish local checks from deployed crawl/index verification. Never promise rankings, indexing, traffic or perfect scores.

Use current primary guidance when requirements are uncertain: [Google's developer SEO guide](https://developers.google.com/search/docs/fundamentals/get-started-developers), [SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide), and the [Open Graph protocol](https://ogp.me/). This checklist follows the shared risk-based workflow and required checkpoints; it does not authorize external submissions, deployment or changes outside frontend ownership.
