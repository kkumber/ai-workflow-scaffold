# Workflow procedures

Shared policy is canonical in [AGENTS.md](../AGENTS.md); concrete project bindings and setup state are in [PROJECT.md](../PROJECT.md), navigation in [ARCHITECTURE.md](../ARCHITECTURE.md). Read only the procedure needed for the current work. This guide is not a mandatory startup read.

## Adoption and managed updates

Use the root [README.md](../README.md) for exact npx initialization, update, resolve and legacy-role migration commands. Installation alone does not place guidance at the project root or adapt it. Preserve existing instructions and the receiving project's manifest/README. Package and CLI copy only eight Markdown guides/forms plus three .codex/agents/*.toml roles; source TASK-* history is excluded, not deleted. Review legacy roles and staged TOML before explicit resolution; old custom roles are never automatically deleted.

Keep .ai-workflow-scaffold/ baselines, pending artifacts and migration backups while needed; they are active tracking/recovery state. Follow documented update/resolve procedures, preserve edited incoming artifacts and inspect clean merges for meaning. Never reset state to force success or assume a selected older package fetches a newer revision.

## First-use procedure

If this is the first use or setup stage, the orchestrator must adapt the existing Markdown guideline files to the receiving project before starting application work. Use their existing structure as the reference: change specific project wording, stack/version details, paths, architecture entries, commands, and conventions; do not regenerate the documents or replace their shared policies. Final cleanup may remove obsolete setup-only sections and artifacts after their purpose is fulfilled.

1. **Detect:** read the setup record in PROJECT.md. Missing state, `template`, or `in progress` means setup is incomplete. A user setup request or observed mismatch between a `ready` record and the current project also requires a setup check. Do not initialize this scaffold source as an application when the user is maintaining the reusable template itself.
2. **Locate:** establish the receiving project root from the user's workspace and existing project configuration. Use paths relative to that root. Do not configure the installed package or this template source as though it were the receiving application. If a multi-project workspace has no unambiguous target, resolve the target before edits. If guidelines exist only in an installed dependency, integrate them into project-owned files first using the user's setup authorization; merge an existing AGENTS.md instead of replacing it. Do not patch dependency copies.
3. **Inspect:** after the scoped orientation in AGENTS.md, inspect the top-level structure, relevant manifests/lockfiles, existing local instructions, test/build configuration, and meaningful entry points. A bounded structure inspection is allowed for initial mapping; do not read all application source. Record evidence paths. A manifest constraint is not a verified installed version; a configured command is not a passed test.
4. **Bind:** set setup status to `in progress`. Make minimal edits to the project-specific fields and wording in README.md (or the existing root README using the project's filename convention), PROJECT.md, ARCHITECTURE.md, AGENTS.md, .codex/agents/\*.toml instructions, tasks/README.md, and reusable task forms only where needed. Adapt the root README's title, purpose, installation, and setup instructions to inspected project facts; merge existing content and preserve user customizations. Preserve valid TOML and the role names, medium backend/frontend reasoning, high reviewer reasoning, and omitted model selection unless the user explicitly changes these preferences. Model selection remains with the user's Codex session/default settings; do not add a per-role model or modify .codex/config.toml as routine setup. PROJECT.md is the canonical source for concrete ownership paths and commands; reference it elsewhere rather than duplicating those facts. Preserve reusable headings, checklist fields, IDs/placeholders for future tasks, readability rules, role boundaries, test-first checks, approval requirements, and reporting style. Remove source-only references from live receiving-project guidance when their targets were not copied; do not rewrite historical task records or manufacture completed tasks.
5. **Handle gaps:** do not choose a stack, business rules, architecture, tooling, or application layout on the user's behalf. For a blank project, map the files that actually exist and leave implementation-dependent values explicitly unknown. Mark an absent role `Not applicable` with an observed reason, not an invented folder. Keep setup `in progress` only if an unresolved decision prevents accurate setup; otherwise record nonblocking unknowns and resolve them before dependent work. Do not install dependencies or create an application just to fill fields.
6. **Clean up:** after receiving-project bindings are established, remove obsolete scaffold wording, example commands, one-time installation/adoption tutorials, completed setup checklists, and source-only maintenance sections that no longer serve the project. Setup-only sections and their headings may be removed despite the initial structure-preservation rule. Keep real project installation instructions and reusable setup/resume rules. Remove a scaffold-only file or folder only after inspecting its contents and references and confirming it is disposable, contains no user work or required evidence, and is no longer used. Record exact removals and reasons in PROJECT.md before deletion. Verify resolved targets stay within the receiving project and delete only identified artifacts; never use a blanket tasks/ or TASK-* deletion. Preserve shared policies, useful project content, active roles, tasks/README.md task-operation guidance, tasks/_template/ future forms/placeholders, the receiving project's actual task history, and setup evidence/status. Do not delete or personalize installed dependency/cache copies. Retain uncertain items and record the question instead of guessing. This cleanup applies to adoption, not maintenance of this reusable scaffold source.
7. **Verify:** check edited paths/links against actual files, ownership consistency, requirement references, preserved policies, configured commands, and cleanup removals. Repair references to removed content and confirm the remaining workflow is usable. Record which checks ran and which commands were only discovered. Do not claim application verification from document inspection. Record affected files, evidence, limitations, and next actions in the setup record and task evidence when a task exists.
8. **Finish:** set status to `ready` only when the target is identified, relevant bindings are accurate, applicable cleanup is complete, links resolve, shared policies are preserved, and no blocking setup decision remains. Report adapted files, removed wording/sections/files/folders with reasons, retained uncertain items, and remaining unknowns. `ready` means documentation is configured, not application tests passed or deployment is ready. On later reads, retain a matching ready configuration; update only changed bindings or explicit user requests. Resume partial setup without wiping completed entries or user customizations.

This is a narrow, orchestrator-only documentation setup permission, not authorization to implement application features, add dependencies, execute migrations, or deploy. It requires no separate application test checkpoint; report direct document checks and honor higher-priority permissions. All application steps still require the [test-first user checkpoint](../AGENTS.md#test-first-cycle-repeat-for-each-coherent-step). Reviewers only report setup gaps; they must never run adaptation edits. If existing project policies conflict with the scaffold, preserve them and resolve the conflict rather than silently overwriting or weakening either policy.

Installing a package does not by itself ensure that the host reads its AGENTS.md or places guidelines in the project root. Markdown guidance alone does not implement package delivery; verify the actual CLI/copy path described in the [root README](../README.md) before claiming first-use setup is reachable.

When managed updates are used, `.ai-workflow-scaffold/` is active tool state, not disposable setup scaffolding. Preserve its saved upstream baselines and pending review artifacts during adaptation/cleanup. Use the documented update/resolve commands instead of resetting state to make an update appear successful. The updater can combine non-overlapping textual changes; review results for project meaning and manually resolve overlapping edits or unknown legacy originals. Do not reintroduce removed setup sections merely to match a template, and do not count a clean text merge as application verification.
## Create a task

Inspect the receiving ledger to select an unused TASK-NNN ID. Copy [plans.md](_template/plans.md) first; choose its short form for small bounded work or expanded form for complexity/risk, then remove unused form instructions. Both retain scoped requirements, exact files/owners, relevant contracts, steps, criteria, cases and approval evidence. Derive [todo.md](_template/todo.md) actions from those IDs; initialize [done.md](_template/done.md) with no fabricated completion. Replace relevant placeholders; ../README.md links work from sibling task folders. Planning-only requests stop before application changes.

The plan is canonical for requirements, case definitions, approval and verification results. Todo holds pending actions, current stage, blockers and next action. Done records completed IDs/behavior and links canonical evidence; do not repeat the complete plan or verification table. Completed history remains available for relevant prior decisions, not routine startup reading. Store verbose logs outside guidance where practical; retain commands, results, meaningful failure excerpts and evidence locations in the plan. Never store secrets or private data.

## Execute, review and resume

Follow [AGENTS.md](../AGENTS.md#test-first-cycle-repeat-for-each-coherent-step) for tests, classification, test-quality review, the explicit user checkpoint, implementation and closure. Link that policy rather than maintaining a second version here. Each coherent step has its own approval; backend approval does not approve dependent frontend implementation. Use direct checks for documentation and proportionate verification as defined there.

Use the assigned [backend](../.codex/agents/backend.toml), [frontend](../.codex/agents/frontend.toml) or [reviewer](../.codex/agents/reviewer.toml) duties only when relevant. Concrete paths come from PROJECT.md and the active plan. Stabilize contracts before dependent implementation; mocks disclose their limits. Shared files have one owner; reviewers report without edits. If delegation is unavailable, declare sequential phases and label review self-review. Provide focused handoffs rather than entire chat histories.

States: planned → tests in progress → awaiting user approval → implementation in progress → in review → done. Test-quality review is part of tests in progress; in review means post-implementation. Blocked/cancelled entries retain reason and last valid stage; cancellation is not completion. Resume using the root scoped-context rule, current plan/todo and only relevant evidence. Confirm approval and intervening changes before reusing results. Move individual completed IDs to done only after all closure conditions; leave other entries pending.

Update affected architecture entries when responsibilities, important locations, contracts or commands change. Follow the root concise-report defaults: brief progress updates, compact approval summaries, usually 3–5 bullets for final responses, and findings/evidence references in handoffs. Link the exact file/case/result inventory; do not recite it in chat unless needed for a decision or requested. Update changed ledger facts only. Expand for important risks or necessary detail; never reduce code quality, required guidelines or verification to shorten output. Passing tests support covered behavior, not universal correctness.

## Marketing SEO checklist

Frontend must read this complete checklist before planning, changing or reviewing public marketing/content pages or affected metadata, crawlability, social previews or search-discovery behavior. Other owners read the relevant portions when their assigned changes affect those contracts. Derive relevant criteria and verification from it; internal/private applications do not become indexable by default.

Treat SEO as a core acceptance concern for public marketing websites, landing pages, and other content intended for search discovery. Plan it alongside content, accessibility, and performance. Establish the audience, page purpose, search intent, approved keyphrases, public domain, and indexing requirements from project evidence and the active plan. Apply only relevant checks to internal applications or deliberately private pages; do not make them indexable by default.

- **Search intent and keyphrases:** give each important page a clear topic and useful, original content that answers its audience's needs. Use approved primary and related keyphrases naturally in titles, headings, visible copy, descriptive links, and appropriate URLs. Avoid keyword stuffing, hidden text, invented search-volume claims, or treating a meta keywords tag as an optimization strategy.
- **Page metadata:** provide a unique, descriptive `<title>` and useful meta description for each indexable page. Use the framework's established metadata system, the correct document language and viewport, and an accurate absolute canonical URL where appropriate. Ensure route-specific metadata updates correctly; avoid duplicate tags and leaking development domains or placeholder branding.
- **Semantic HTML:** use meaningful landmarks such as `header`, `nav`, `main`, and `footer`, plus `article` and `section` where appropriate. Give each page a clear primary heading and a logical heading hierarchy. Use real anchor links with descriptive text for navigation, buttons for actions, accessible labels, and meaningful image alternatives; decorative images use empty alt text. Do not choose tags only for their visual styling or add keyphrases to unrelated alt text.
- **Open Graph and social media:** supply accurate `og:title`, `og:description`, `og:type`, `og:url`, and `og:image`, plus image alt text and dimensions when known. Add suitable social-card metadata for the intended platforms. Use approved, relevant preview media with absolute, publicly reachable URLs and valid media types. Keep preview titles, descriptions, canonical URLs, and branding consistent with the page; verify media availability and actual previews where tooling permits. Social previews support sharing and are not a promise of search ranking gains.
- **Crawlable content and routes:** make important copy, metadata, and navigation available to crawlers using the project's established rendering approach. Prefer server-rendered or statically generated marketing content when supported; do not assume every crawler or preview service executes client JavaScript. Use stable, meaningful URLs and crawlable links. Verify intended status codes, redirects, canonical behavior, and missing-page behavior through the responsible owner.
- **Indexing and discovery:** coordinate accurate sitemap entries, robots directives, canonical rules, and `hreflang` for actual localized equivalents when relevant. Include only intended canonical, indexable URLs in sitemaps. Check that public production pages are not accidentally marked `noindex`; keep staging/private content protected according to project requirements. Robots directives are not access control. Server headers, redirects, authentication, and infrastructure changes require their assigned owner and checkpoint.
- **Structured data:** use relevant supported schema only when it accurately represents visible page content and verified business facts. Validate it with appropriate tooling when applicable. Never fabricate reviews, ratings, locations, offers, or eligibility claims to obtain rich results.
- **Media and performance:** optimize image formats, responsive sizes, compression, dimensions, fonts, scripts, and loading behavior. Avoid lazy-loading the primary above-the-fold image when it harms loading performance; defer offscreen media where appropriate. Check mobile usability, layout stability, and relevant Core Web Vitals using available evidence. Do not trade away accessibility or useful content for an audit score.
- **Verification and handoff:** derive SEO cases from the affected pages and approved requirements. Inspect initial HTML and rendered output, titles/descriptions/canonicals, headings, indexability, links, and social media assets. Use existing automated checks and focused browser/audit tools where appropriate; record actual results, inaccessible production-only checks, and remaining owner actions. Distinguish local audits from deployed crawl/index verification. Never promise rankings, indexing, traffic, or perfect scores.

Use current primary guidance when requirements are uncertain: [Google's developer SEO guide](https://developers.google.com/search/docs/fundamentals/get-started-developers), [SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide), and the [Open Graph protocol](https://ogp.me/). This checklist does not waive the shared test-first approval cycle or authorize external submissions, deployment, or changes outside frontend ownership.
